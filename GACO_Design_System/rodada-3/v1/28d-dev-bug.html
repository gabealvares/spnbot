Ficha da tela Bug com passos para reproduzir, esperado e obtido, e clientes afetados.

O que esta tela resolve

Quem corrige precisa reproduzir em minutos. O bug traz versão, ambiente, passos numerados, esperado contra obtido, o log e os chamados de origem, e quem atende sabe o que dizer ao cliente.

Fluxo

  1. O Suporte cria o bug a partir do chamado; o chamado fica ligado e é avisado quando o bug muda de estado.
  2. O desenvolvedor assume ("Assumir"), reproduz e marca "Reproduzido em homologação".
  3. O PR ligado aparece em "Correção"; ao mesclar, o bug vai para QA com a versão.
  4. "Avisar clientes" manda a resposta pronta nos 3 chamados quando a versão é publicada.

Resolvemos fazer assim porque

o modelo de relatório de bug do Jira e do GitHub Issues (passos, esperado, obtido, ambiente) é o que o time já escreve; o Linear e o Zendesk ligam o bug ao ticket e avisam o atendente; o Sentry mostra o erro com o contexto. Severidade é palavra, não só cor.
